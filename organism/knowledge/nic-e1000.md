# NIC — Intel 82540EM Gigabit Ethernet (e1000) @ 00:03.0

Target: PCI `00:03.0`, vendor:device `8086:100E`, class `020000` (Ethernet controller).
Probed read-only through `hw.py` against the QEMU-hosted AgentZero kernel (127.0.0.1:50000).

## 1. Identity

- `8086` = Intel, `100E` = the 82540EM "e1000" Gigabit Ethernet controller — QEMU's
  default emulated NIC. Class `02 00 00` = Network controller / Ethernet / generic.
- This is the machine's only network interface. It is a well-understood, fully
  documented device (Intel 8254x "PCI/PCI-X GbE Controllers" SDM), which makes it a
  good candidate for a real driver skill later.

## 2. PCI config space (full 256 bytes, dwords as read)

```
00: 100E8086   vendor=8086 device=100E
04: 00000107   command=0x0107 status=0x0000
08: 02000003   class=020000 rev=03
0C: 00000000   cacheline/latency/header=00/00/00 (type 0, single-function)
10: FEBC0000   BAR0 — MMIO, 32-bit, non-prefetchable
14: 0000C001   BAR1 — I/O space, base 0xC000
18: 00000000   BAR2 unused
1C: 00000000   BAR3 unused
20: 00000000   BAR4 unused
24: 00000000   BAR5 unused
28: 00000000   cardbus CIS = none
2C: 11001AF4   subsystem vendor=1AF4 (Red Hat/QEMU) subsystem id=1100
30: FEB80000   expansion ROM base = 0xFEB80000 (BAR disabled bit0=0)
34: 00000000   capabilities pointer = 0x00 (none exposed here)
3C: 0000010B   int line=0x0B(IRQ11) int pin=0x01(INTA) min_gnt/max_lat=00
40..FC: all zero
```

### Decoded fields (citing the dwords)

- **Command `0x0107`** (dword 0x04 low half): bit0 I/O Space Enable=1, bit1 Memory
  Space Enable=1, bit2 Bus Master Enable=1, bit8 SERR#=1. So the device is already
  decoding both its BARs and is allowed to be a bus master (DMA-capable) — important
  for descriptor-ring operation.
- **Status `0x0000`** (dword 0x04 high half): no capabilities-list bit set here and
  cap pointer (0x34) reads 0x00 — this QEMU e1000 model exposes no PCI capability
  chain (no MSI/PM capability advertised in config space). Legacy INTx is the
  interrupt path.
- **Class `020000`** (dword 0x08 bits 8..31), **revision 0x03** (low byte).
- **BAR0 = `0xFEBC0000`** (dword 0x10): bit0=0 → memory BAR; bits[2:1]=00 → 32-bit;
  bit3=0 → non-prefetchable. Physical MMIO base = **0xFEBC0000** (below 4 GiB, so
  readable with `hw.py mem`). This is the e1000 register block. Size is not probed
  (sizing needs a write to the BAR, which is forbidden); the 82540EM register region
  is architecturally **128 KiB (0x20000)**.
- **BAR1 = `0x0000C001`** (dword 0x14): bit0=1 → I/O-space BAR. I/O base = value &
  ~0x3 = **0xC000**. This is the e1000's I/O-mapped IOADDR/IODATA window (an
  alternate, indirect path to the same registers). Size architecturally 64 bytes.
- **Expansion ROM `0xFEB80000`** (dword 0x30): a boot-ROM (PXE) window; enable bit0=0
  so it is currently disabled.
- **Subsystem `1AF4:1100`** (dword 0x2C): 1AF4 is the Red Hat / QEMU subsystem vendor,
  confirming this is the virtualized 82540EM.
- **Interrupt `0x0000010B`** (dword 0x3C): INTA# routed to **IRQ 11** (int line 0x0B).

## 3. Live MMIO registers (read via `hw.py mem 0xFEBC0000+off`)

Note a kernel quirk: the `mem` primitive returns each MMIO register's **low byte
replicated** across the 4 byte lanes (e.g. STATUS reads back as `83 83 83 83`). Only
the low byte of each 32-bit register is recoverable this way; the values below are
the low bytes, interpreted against the known e1000 register layout.

| off     | reg    | low byte | meaning |
|---------|--------|----------|---------|
| 0x0000  | CTRL   | 0x60     | device control (low byte; ASDE/SLU-region bits) |
| 0x0008  | STATUS | 0x83     | **link up** |
| 0x5400  | RAL0   | 0x52     | MAC byte 0 = 0x52 |
| 0x5404  | RAH0   | 0x34     | MAC byte 4 = 0x34 |

- **STATUS low byte 0x83 = 1000_0011**: bit0 FD=1 (full duplex), bit1 LU=1 (**link
  up**), bits[7:6]=10 → SPEED = 1000 Mb/s. The link is up at 1 Gbps, full duplex.
- **RAL0 low=0x52 / RAH0 low=0x34**: the Receive Address registers hold the station
  MAC in little-endian (RAL = MAC[0..3], RAH = MAC[4..5]). Low bytes 0x52 (MAC[0]) and
  0x34 (MAC[4]) match QEMU's default e1000 MAC **52:54:00:12:34:56** — the standard
  52:54:00 (QEMU) OUI. (Full bytes not recoverable through the low-byte-only reader.)

## 4. How one would drive it (e1000 driver sketch — not yet implemented)

Config already has Memory + Bus Master enabled, so a driver can go straight to the
register block at BAR0 (0xFEBC0000). Standard 82540EM bring-up:

1. **Reset / control**: write CTRL (0x0000) RST bit, re-read; set ASDE+SLU (auto-speed
   + set-link-up). Clear multicast table array (MTA, 0x5200..).
2. **EEPROM / MAC**: read MAC from RAL0/RAH0 (0x5400/0x5404) — already populated.
3. **RX ring**: allocate receive descriptor ring (16-byte legacy descriptors: buffer
   addr, length, status). Program RDBAL/RDBAH (0x2800/0x2804), RDLEN (0x2808),
   RDH/RDT (0x2810/0x2818). Set RCTL (0x0100): EN, BAM (broadcast), buffer size, SECRC.
4. **TX ring**: allocate transmit descriptor ring. Program TDBAL/TDBAH (0x3800/0x3804),
   TDLEN (0x3808), TDH/TDT (0x3810/0x3818). Set TCTL (0x0400): EN, PSP, collision
   thresholds; TIPG (0x0410).
5. **TX a frame**: fill a descriptor (buffer phys addr, length, CMD EOP|IFCS|RS),
   bump TDT; poll descriptor DD status bit for completion.
6. **RX a frame**: poll the head descriptor's DD bit (or take IRQ11), read buffer,
   advance RDT.
7. **Interrupts** (optional): ICR (0xC0), IMS (0xD0), IMC (0xD8). Legacy INTA→IRQ11.

All of this requires **physical-memory writes + MMIO writes** (descriptor rings and
register programming), which are gated and must be proposed as a reviewed write-skill
before being armed.

### Status: first gated MMIO writes performed (`skills/nic-mmio-write.py`)

Using the kernel's gated `W<addr><dword>!` primitive (hw.write32), the organism has
now **operated** this NIC's registers for the first time, in QEMU:

- **MMIO write path proven:** wrote a sentinel `0xA5` to MTA[0] (0x5200), read its
  low byte back as `0xA5`, then restored `0x0` (read back `0x00`). Fully reversible;
  MTA is inert while RX is disabled. STATUS stayed `0x83` (link up) throughout.
- **RDLEN (0x2808) staged** to 0xF000 safely (plain R/W, inert until RCTL.EN).
- **RDBAL (0x2800) is NOT safe via this path:** writing RDBAL = 0x00040000 **wedges
  the kernel** in QEMU — the write acks, then the machine stops answering (even CPUID
  times out). Reproduced on clean boots; RDBAH (0x2804) = 0 is harmless, only RDBAL
  triggers it. Root cause not yet understood (suspected QEMU e1000 ring-recompute /
  descriptor-fetch side effect). **Held back** by the arm-in-sandbox gate: it is a
  proposal, never armed, so it has not touched real hardware. Investigate before any
  RX ring base programming (e.g. single-step register writes while watching STATUS/
  ICR, or a full-dword MMIO reader to see what the write actually set).

## 5. Open questions

- The `mem` reader only returns each register's low byte; full 32-bit MMIO reads
  (and thus exact CTRL flags, full MAC, ICR, etc.) need a kernel readout that
  preserves all four bytes, or the I/O-indirect path via BAR1 (0xC000: write IOADDR,
  read IODATA — also needs port writes).
- BAR0/BAR1 sizes assumed from the architecture (128 KiB / 64 B); not probed because
  sizing requires writing all-ones to the BAR (forbidden read-only).
- No PCI capability chain is exposed (cap ptr 0x00) — so no MSI/MSI-X/PM here; confirm
  whether QEMU's `-device e1000` variant would differ.
- Driving the NIC (RX/TX) is a future **write-skill**, to be gated and reviewed. The
  first gated MMIO writes are done (see Status above); the RX-ring-base wedge is the
  next thing to understand before RX bring-up can proceed.
